# ADR-0001：使用 Pi 作为 Agent 运行基础

- 状态：已采纳
- 日期：2026-07-30
- 相关任务：[TASK-001](../tasks/TASK-001-file-organization.md)
- 取代：无
- 被取代：无

## 背景

项目需要模型接入、Agent 循环、Tool 调用、会话、Skill 和扩展能力。直接从头实现这些能力会增加学习和维护成本，也无法达到通过实际产品深入理解 Pi 的目的。

同时，产品还需要任务状态、办公文件、权限确认、审计、连接器和界面。这些内容不应直接写入 Pi 内部模块，否则后续升级 Pi 或更换接入方式时会影响整个产品。

## 决定

使用 Pi 作为 Agent 运行基础，优先复用其模型、Agent、Tool、会话、Skill、Extension、SDK 和 RPC 能力。

产品功能通过明确的适配边界调用 Pi。业务场景、任务状态、权限、审计、办公文件和外部系统连接器属于 PiDesk，不写入 Pi 内部实现。

第一批场景会通过实际代码决定使用 SDK 还是 RPC。该选择确认后单独创建 ADR。

## 原因

- 可以在真实场景中学习 Pi；
- 避免重复实现通用 Agent 能力；
- 保持 Pi 与产品功能的职责清楚；
- 降低 Pi 升级和产品扩展的相互影响。

## 影响

### 正面影响

- 第一批场景可以更快进入可运行状态；
- Agent 能力可以跟随 Pi 持续升级；
- 产品层可以独立增加办公功能；
- 后续可以清楚说明 Pi 提供了什么、项目实现了什么。

### 代价和限制

- 需要维护稳定的适配接口；
- 开发前需要理解 Pi 的公共 API 和生命周期；
- Pi 公共接口变化时需要更新适配层；
- 不能为了方便让业务代码直接依赖 Pi 内部类型。

## 考虑过的方案

### 从头实现 Agent 运行层

可以完全控制实现，但会把主要时间用于重复建设模型接入、工具循环和会话机制，不符合项目的学习和交付目标。

### 直接修改 Pi 内部代码形成产品

短期修改方便，但会混合上游能力和产品逻辑，使升级、测试和私有环境复用更加困难。

## 重新评估条件

- Pi 无法支持关键办公场景；
- Pi 公共接口无法形成稳定适配边界；
- 维护适配层的成本长期高于替换运行基础；
- 项目的运行环境与 Pi 支持范围发生根本冲突。
