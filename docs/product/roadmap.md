# 产品路线

本路线描述 DeskBuddy 的能力演进顺序，不代表固定发布日期。每个阶段都必须形成可运行、可检查的纵向切片，未通过验证的能力不提前扩张。

## 阶段 0：项目基础

状态：已完成。

### 目标

- 建立产品目标、场景、任务、ADR 和 Changelog 的职责边界；
- 建立 React 工作台原型和公开仓库规则；
- 使用公开资料、模拟数据和确定性测试验证候选方案；
- 让当前任务、验证结果和下一步可以从仓库恢复。

## 阶段 1：确认 Pi 运行架构

状态：收尾中。

[TASK-001](../../tasks/TASK-001-file-organization.md) 使用文件重命名作为 SDK 边界实验；[TASK-003](../../tasks/TASK-003-pi-runner-architecture.md) 在 Pi `0.84.2` 上确定桌面产品的正式运行架构。

### 已确认结论

- Pi 是唯一 Agent 执行器；
- 产品采用 Electron + React；
- Pi SDK 位于独立 Runner；
- Electron Control Plane 通过 Pi 官方 JSONL RPC 控制 Runner；
- Pi JSONL 保存会话树，SQLite 保存 DeskBuddy 产品元数据；
- Renderer 不拥有文件系统、凭据或任意 Pi RPC 权限；
- V1 全局只允许一个活动 AgentRun，并只开放受控只读工作区 Tool。

### 完成条件

- 架构规范和 ADR-0003 已采纳；
- 旧产品、路线、学习和开发流程文档与当前决定一致；
- 第一个实现切片具有可直接执行的实施计划。

## 阶段 2：只读代码工作区纵向切片

状态：下一阶段。

这是 DeskBuddy 第一个用户可感知的完整产品功能。目标不是制作聊天演示，而是验证真实本地目录、Pi 执行、产品状态和重启恢复组成的主链路。

### 用户链路

1. 用户通过系统目录选择器授权一个真实代码目录；
2. DeskBuddy 保存 Workspace，并在应用重启后重新验证目录；
3. 用户创建 Task 并提交代码问题；
4. Control Plane 创建 AgentRun、取得会话租约并启动 Pi Runner；
5. Pi 只能调用 `workspace_list`、`workspace_read` 和 `workspace_search`；
6. React 流式显示回答、Tool 进度和确定状态；
7. 用户可以取消运行；
8. 关闭并重启应用后，从 SQLite 和 Pi JSONL 恢复工作区与任务。

### 完成条件

- 使用真实代码目录完成一次只读 Pi 运行；
- 目录缺失时保留历史并允许重新关联；
- 运行可以流式显示、取消，并区分完成、失败、取消和中断；
- Runner 崩溃不影响 Electron Control Plane；
- 同一 Pi 会话没有并发写入；
- Agent 无法通过公开 Tool 读取工作区外文件；
- faux provider 的正常、取消、崩溃和恢复测试通过。

## 阶段 3：受控代码修改

只有阶段 2 稳定后才开放写能力。

### 目标

- 增加修改方案和变更预览；
- 将用户批准绑定到确定的文件、参数和内容摘要；
- 使用受控 Tool 执行修改，不直接开放无限制 Shell；
- 检测文件变化、越界、冲突和重复执行；
- 保存可检查的 diff、执行结果和恢复信息。

### 完成条件

- 未批准的修改不会执行；
- 实际修改与批准内容一致；
- 工作区外文件不能被修改；
- 冲突和执行前变化有确定结果；
- 失败不会被模型文字伪装成成功。

## 阶段 4：办公能力包

代码工作区主链路稳定后，在相同任务、工作区、审批、产物和持久化机制上增加办公能力。

候选顺序：

1. 工作区中的文档资料整理与生成；
2. 会议材料和行动项；
3. 表格分析；
4. 演示文稿生成与修改；
5. 网页调研与结果整理。

能力包可以组合受控 Tool、确定性服务、第一方 Skill/Extension 和声明式界面。完整办公功能不等同于一个 Pi Extension，文件格式处理、外部调用和确定性校验仍由产品服务或受控 Tool 承担。

### 完成条件

- 至少两个场景复用公共任务链路；
- 结果是可检查的文件或结构化产物，不只是一段聊天文字；
- 能力包不能绕过工作区、权限和审批边界；
- Renderer 不执行能力包提供的任意代码或任意界面。

## 阶段 5：办公服务与连接器

### 目标

- 先接入一个只读服务；
- 建立认证和凭据隔离；
- 将查询与修改操作分开；
- 记录外部调用；
- 只在只读流程稳定后增加写操作。

### 完成条件

- Agent 不能获得超过当前用户授权的能力；
- 凭据不进入模型上下文和普通日志；
- 外部写入可预览、可确认并防止重复执行；
- 限流、超时、授权过期和接口错误有明确结果。

## 阶段 6：沉淀可复用能力

只有一种工作方法已经在多个任务中稳定出现时，才整理为 Skill、模板、公共 Tool 或能力包。稳定的角色、默认上下文、Skill 和工具组合可以形成助理或专家，但不能自动扩大权限。

### 完成条件

- 新场景可以组合既有能力，不必复制整套流程；
- 能力说明包含适用条件、依赖、输入、输出和失败处理；
- 更新后有固定样例验证；
- 复用不会自动扩大 Tool 权限。

## 阶段 7：自动任务、远程入口与多 Agent

这些能力不是产品成熟度指标，只在前置手动链路稳定且存在可测量收益时进入。

### 前提

- 对应手动任务已经稳定；
- 超时、重试、并发、幂等和无人值守权限边界已经验证；
- 多 Agent 具有可以独立检查的分工，并相对单 Agent 改善质量、速度或成本；
- 远程入口能够正确识别用户、设备和授权范围。

## 每个阶段的交付物

- 场景或架构规范；
- 开发任务和唯一下一步；
- 必要的 ADR；
- 测试样例和实际验证结果；
- 使用说明和安全边界；
- 用户可以检查的最终结果。

## 完成标准

不以页面数量、模型数量、Skill 数量或是否使用多 Agent 判断完成。真正的标准是：目标用户能完成指定工作，结果可检查，失败可处理，风险受控制。
