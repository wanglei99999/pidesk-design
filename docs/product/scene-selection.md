# 场景筛选和分析方法

## 场景来源

DeskBuddy 的场景可以来自：

- 自己反复完成的办公任务；
- 公开、可复现的办公流程；
- 市面产品已经验证的业务场景；
- 用户反馈和公开需求；
- 已完成场景暴露出的下一步需求。

不要先问“能加什么 AI 功能”。先写清楚用户当前怎样完成工作、输入来自哪里、需要交付什么、哪一步最耗时以及做错后的影响。

## 场景记录

新场景从 [场景模板](../scenarios/TEMPLATE.md) 创建。场景文件负责说明需求、边界、风险和验收，不负责记录开发进度。

至少写清：

| 字段 | 说明 |
|---|---|
| 用户和问题 | 谁遇到什么具体问题 |
| 当前做法 | 现有人工或软件步骤 |
| 输入 | 文件、网页、数据或用户指令 |
| 输出 | 文档、表格、消息、文件变更或系统记录 |
| Agent 工作 | 需要模型理解、判断或生成的部分 |
| 程序工作 | 权限、状态、校验、冲突和写入 |
| 风险 | 泄露、误删、误发、覆盖、错误计算等 |
| 验收 | 如何证明结果可用、系统行为正确 |

## 筛选条件

优先选择：

- 可以使用公开或模拟数据；
- 输入和输出比较稳定；
- 第一版范围可以明确收窄；
- 结果容易检查；
- 出错后可以停止或恢复；
- 能增加后续场景可复用的能力；
- 自己可以完成使用和验收。

谨慎选择：

- 依赖大量无法说明的隐性经验；
- 结果没有明确评价方法；
- 直接影响资金、合同、客户或生产数据；
- 第一版就需要多个外部系统；
- 只能依赖不稳定的页面自动化；
- 无法准备合法、可公开的测试样例。

## 从场景到任务

场景进入开发前：

1. 选择一个最小可运行范围；
2. 明确本次不做什么；
3. 准备正常、边界和失败样例；
4. 将实现工作写入独立 TASK；
5. 在 [TASKS.md](../../TASKS.md) 登记状态、开发位置和下一步。

一个场景可以拆成多个任务。不能为了“一次做完场景”把解析、连接器、界面和自动任务全部放进第一版。

## 区分模型质量和系统正确性

模型质量包括摘要、分类、提取和生成内容是否合理。它可能随模型变化，需要固定样例、评分或人工检查。

系统正确性包括权限、状态、确认、取消、冲突、重复执行和操作记录。它不能依赖模型自由决定，必须由普通程序和自动测试保证。
